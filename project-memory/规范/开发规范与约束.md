写给在本仓库写代码的人和 agent。目录表、命令、怎么写一个页面、数据库的写法、红线清单在根目录的 `AGENTS.md`，内核的细节在 `core/CORE.md`，这里不重复。这里讲原则：每条先写规矩，再写理由，下面的列表是做法。agent 怎么和维护者配合，见《agent 工作规范与约束》。

## 一、代码准则

### 1. 每次动代码都按六个词：认真、负责、严谨、简洁、高效、封装化

**理由**：这个框架要的是轻量、规范、一目了然。这六个词是维护者给代码定的标准，不只管某一块、某一次。

- **认真、负责**：加任何东西之前先答三个问题，并写进汇报——现在有没有人用得上；会带来什么别的后果；Windows、Linux、macOS 上各是什么表现。答不出"现在谁用得上"的，不加。
- **严谨**：先把现有的代码和它依赖的库读明白再动手，库的行为以源码为准，不凭印象。出错和边界情况都要有明确的去处；和安全有关的地方，拿不准时宁可拒绝。配置写错要在启动时报出来，不带着错的配置跑（例如数据库配置、`JwtSecret`、`ProxyTrusted`、`PprofAddr`、日志目录，有问题都不启动；`LoadRuters` 写错现在只记日志、照常启动，是还没有改的地方）。
- **简洁**：只写现在用得到的，不为"以后可能"加类型、参数、开关。一件事只留一种写法。
- **高效**：每个请求都要走的路上不做多余的事（反射、来回转 JSON、多余的内存分配、多余的数据库往返）。说"更快"要有改之前和改之后量出来的数字，变慢的地方也照实说。
- **封装化**：规则放进它该在的那个包、那个函数里，调用的地方只剩一句。对外的名字少而清楚，内部细节不露出去；调用方式能不变就不变。

### 2. 不过度设计，不过度封装

**理由**：为眼下用不上的情况加的一层函数、一个返回值、一个开关，读的人每次都得弄懂它，还可能带来没有想到的后果。

- 加一层函数、一个返回值、一个配置项之前，先看现在有没有代码用得上；只是为以后可能出现的情况，就不加，报给维护者一句。
- 做完看有没有因为这次改动而没人调用的代码、只转一手的包装，连同"谁在调用"的结果报给维护者，他点头再删。（这说的是改动留下的边角；已有的功能见第 7 条。）
- 会让进程崩、丢数据、绕过鉴权的地方，严谨排在简洁前面；多出来的代码在注释和汇报里说清它挡的是什么（例如基础中间件里外两层 panic 兜底）。只是"以后可能用到"不算严谨。别的冲突，把两种做法和各自的代价摆给维护者定。

### 3. 名字直接说出它是什么

**理由**：`root`、`base` 这类词要靠上下文才知道指什么，还容易和"root 用户""根目录"混，没看过上下文的人会读错。

**做法**：日志目录就叫 `logDir`；同一个意思的字段、参数、局部变量用同一个名字。已有的名字能沿用就沿用，改名要写明理由。

## 二、架构约束

### 4. 内核（`core/`）只做基础设施，业务的约定放 `syscore/`

**理由**：内核一旦知道业务怎么分发请求、怎么判断登录，换一种业务约定就得改内核。边界清楚，内核才小而稳定，上面的业务才换得动。

- 往 `core/` 里加代码、或者把 `syscore/` 的代码收进 `core/` 之前先问：这段代码知不知道业务的约定（页面路径、act、登录、权限、具体的表）？知道就不属于内核。（请求上下文 `core/pncontext` 里从路由参数取 `act`、带着登录信息的接口，是现状；不照这一条去挪，要动先问。）
- 内核不替用它的系统做业务上的判断。"必须有某个库""没有就不启动"这类要求，由装配的地方（`main.go`）或用到它的地方决定：`InitDbPool` 配了几个库就连几个，"没有主库不启动"是 `main.go` 判断的。
- 精简是去掉没人用的东西和重复的样板，不是合并层次。一个目录、一个接口哪怕只有几行（`core/router` 只有一个接口），也可能是一条边界；动它之前先说清这条边界是什么、去掉以后谁来守。
- 现有代码"不够通用"时，把写死的差别变成数据，让一种通用的装法吃这份数据（各组路由的差别就是配置里的名字和前缀）；不给每种差别各建一个类型、一组方法，也不把上层的代码收进内核。
- 依赖是单向的：`core/pncontext` 引用 `core`，`core` 不反过来引用它，也不引用 `syscore`。带业务码的统一错误出口在 `syscore/utils`，内核只通过 Fiber 的 `ErrorHandler` 调它。

### 5. 目录按职责分层，新增代码放进已有的对应目录

**理由**：文件平铺在一个目录里，看不出各自管什么、谁依赖谁；按职责分开，"该放哪"才有依据。

**做法**：内核的能力进 `core/` 下按能力分的子包，业务的约定进 `syscore/`，页面进 `sysmgr/`，登录进 `sysauth/`（各目录放什么见 `AGENTS.md` 的目录表）。不另起一层；要新建目录、调整结构，先问维护者。

### 6. 内核要一目了然，不另起抽象

**理由**：`core/core.go` 从上往下读完就懂整个启动流程，这是"易上手"的根本。另起一套概念，维护者和使用者都得重新学，也对不上已有的代码。

- 照现有的样子写：`SysConfig` 加 `Boot`，`Boot` 的注释按 1、2、3 列出执行顺序；`PreSetup` → 业务路由 → `Setup` 三段；请求上下文 `PnContext`（变量叫 `pnctx`）；控制器的 `Page_<act>` 方法。名字、结构、用法能沿用就沿用。
- 现有框架没有的机制（应用对象、函数式选项、模块生命周期钩子、延后注册、再包一层接口）默认不引入；确实要引入，先说明它解决现有代码的哪个具体问题。
- `core/pnlibs`（并发 map `PnObjects`、队列、雪花 ID、`ExitWatch`）和 `core/pnlogrus` 是项目自带的库，用它们，不另写一套替掉。并发 map 用 `pnlibs.PnObjects`，`pnlibs` 之外不直接用 `sync.Map`（这些库是维护者针对当时 Go 版本里的问题自己设计的）。要改它们，先给分析和数据，把"必须修的"和"顺手改的"分开列，等维护者定。
- 动了内核，`core/CORE.md` 跟着改。

## 三、不精简掉已有的功能

### 7. 现在没有人调用，不等于可以删；功能留着，实现可以改进

**理由**：没人调用只说明现在。去掉一种现成的能力，以后要用就得重新加回来，比留着贵。一种写法背后往往是一种能力：省掉样板是精简，去掉"能这样写"是丢能力。

- 两种页面写法都留着：默认按 `Page_<act>` 方法自动分发；控制器写了 `PageMain` 时请求全部交给它，给不按 act 分的接口用（`syscore/routers/page.go`）。
- ClickHouse 的支持必须保留（`core/database` 支持 PostgreSQL 和 ClickHouse），不要提议去掉。
- 分区管理器里现在没有调用方的方法（`GetPartitions`、`PrintPartitionTreeWithStats`、`RunScheduledTask`）留着。
- 真要提议去掉什么：先在整个仓库里搜它的全部用法（包括路由、中间件这些调用方），把它提供的能力一条条列出来、逐条说明去掉之后由什么承担，把"以后要用得加回来"写进代价，选项里单列"留着、只改进"。报给维护者定，不自己删。

## 四、优雅退出（红线）

### 8. 退出时绝对等待：后台任务和在途请求全部做完才退出

**理由**：后台任务被中途打断会留下不一致的状态（数据写了一半、消息处理了一半），代价远高于退出慢。等到做完是这个框架的设计目的，不是待优化的地方。

- 不加超时，不加强制退出，也不提供"可选、默认关闭"的超时配置。等待期间再来的退出信号只记一条日志，不打断等待。
- 现在的退出顺序（`core/core.go` 里 `Boot` 的最后一段，每一步都等到做完）：`Tasks.Stop()` 等正在执行的定时任务和常驻协程全部结束（这期间 HTTP 还在线，`/readyz` 回 503）→ `exitFn` → `app.Shutdown()` 等在途请求 → 清页面对象池、断开数据库 → 停性能剖析。
- 退出信号是 SIGINT、SIGTERM、SIGQUIT（Windows 上是 Ctrl+C、Ctrl+Break、关闭控制台窗口）。SIGHUP 被忽略，终端断开时服务照常运行。
- 退出信号到 `Boot` 的最后一步（`pnlibs.ExitWatch`）才登记。启动完成之前收到的，进程按系统默认直接结束：这段时间要它退出的只能是人或部署工具，直接退出就是对的。不加"提前登记信号"，那会让启动慢的时候按 Ctrl+C 没有反应。
- 后台的活经任务管理器 `core.GConfig.Tasks`（`AddTask`、`Go`、`RunTask`）启动才在等待范围内，自己 `go` 出去的协程内核不知道；常驻协程要看 `Tasks.Quit()`。`log.Fatal` 那一组直接结束进程，不用。
- 启动失败时 `Boot` 返回错误，进程以退出码 1 结束（`main.go` 的写法见 `AGENTS.md`）。`Boot` 自己失败时先等任务管理器停下；还没走到 `Boot` 的失败不等，所以常驻协程要在各项启动检查之后、紧挨着 `core.Boot` 之前启动。
- 外面的停止超时（`docker stop`、systemd、k8s、Windows 关闭窗口）不归进程管：在部署上调够，不在程序里加超时去迁就。
- 动退出的顺序、信号、等待的语义之前，先问维护者。测退出要发真实的退出信号（Windows 上是 Ctrl+Break），强杀测不出来。

## 五、数据库和分区表

### 9. 分区表照 `db_demo_partition` 的样子设计

**理由**：分区表的主键必须带上分区键，自增 `id` 单独当不了主键，也没有业务含义，一条记录的身份是单号。拿单独一列日期当分区键，分区的范围就是字面上的日期，和时区没有关系。

- 没有自增的 `id`。第一列是单号（`bigint`，雪花 ID，由程序给，不建序列、不给默认值），接着 `created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP`、`created_date date NOT NULL DEFAULT CURRENT_DATE`；主键 `(单号, created_date)`；`PARTITION BY RANGE (created_date)`。
- 每个月的分区由分区管理器建（`core/CORE.md` 的"分区表管理"）；要管的表，往 `main.go` 的列表里加表名。

### 10. 设计表之前先找仓库里同类的表，找不到就先向维护者要一个参照

**理由**：表结构落进库里以后很难改。按自己的习惯建出来的表和已有的约定对不上，就得返工。

**做法**：列名、时间列的类型、建表脚本和升级脚本两处一起改，照 `AGENTS.md` 的"数据库"一节。

### 11. 要落进库里、以后改不动的东西，不跟着程序所在机器的时区走

**理由**：同一份代码会跑在时区不同的机器上（开发机是本地时区，容器不设 `TZ` 是 UTC）。跟着机器的时区走，连同一个库的几个实例建出来的东西对不上：分区重叠会报错；留下空档不报错，到那个时刻写不进数据。

- 提这类建议（分区边界、表结构、存进去的时间）之前，按三种情况各过一遍：几台机器时区不一样；同一台机器的时区以后被改；三个系统的默认时区不同。
- 现在的做法：分区的范围写不带时区的日期，分区键是日期列时和时区无关（`core/pnpartmgr`）；时间列用 `timestamptz`。

## 六、三个系统都要过

### 12. 每处改动都过一遍 Windows、Linux、macOS：编不编得过，各是什么表现

**理由**：部署以 Linux 为主，开发常在 Windows 上，三个系统在信号、文件权限、路径、终端上的行为不一样。"主要运行在 Linux"不等于别的系统可以不认真考虑。

- 三个系统各编一遍（命令见 `AGENTS.md`），汇报里各写一句表现；和信号、文件、路径、进程有关的改动尤其要想清楚。
- 不用只在一个系统上才有的办法（例如给自己发信号，Windows 上没有）。
- 提方案、排优先级按 Linux 上的表现来。Linux 上才有的事要主动想到并报出来：文件权限、systemd 和容器的停止超时、标准输出不是终端（颜色码会原样带出去）、符号链接、路径大小写。
- 涉及某个系统的结论先实测再说；没有实测的，照实说是按源码判断的。
- 已经定了保持原样、不为它专门写代码的两件：在传统的 Windows 控制台窗口里选中文字，写日志的地方会停住；日志的日期目录名带方括号（在 PowerShell 里是通配符）。

## 七、编译产物和日志

### 13. 编译产物一律放 `_bin/`，服务进到 `_bin/` 里启动

**理由**：调试和发布要一个固定的地方。配置、模板、前端文件、上传目录都只按当前目录找，不进到那里启动就找不到。

- 后端由编译脚本输出到 `_bin/`，前端构建后把 `web/dist` 复制成 `_bin/public`（命令见 `AGENTS.md`）；不往仓库根目录或别处放编译产物。`_bin/` 整个不进仓库。
- 重新编译之前先停掉正在跑的服务（Windows 上运行中的可执行文件盖不掉）。别人正在跑的服务不要去停，这时把可执行文件编到草稿目录（仓库之外的临时目录）里测。
- 配置项有增减时，`_bin/conf/` 里那一份跟着改。

### 14. 日志文件是 `logs/[日期]/<进程名>-<进程号>-mylog.log`，默认在可执行文件所在的目录下

**理由**：几个进程写同一个日志目录时，靠进程名（不同的程序）和进程号（同一个程序的几个进程）分开。日志跟着可执行文件走，从哪个目录启动都找得到。

- 不往文件名里加主机名：它只对"几个容器共用一个日志目录"有用，那种部署应当让每个容器用各自的 `LogDir`。
- 默认的目录（可执行文件旁边的 `logs`）和可选的配置项 `LogDir` 都保留，不提议去掉哪一个。目录没有就自己建；建不出来、没有权限写，服务不启动。
- 其余已经定下的（文件权限 0640、标准输出不是终端时不带颜色码、`LogFileOnly`、`LogKeepDays`、时区）见 `core/CORE.md` 的"日志"。
- 清理过期日志会删目录：测保留天数要用编到草稿目录的可执行文件和自己的日志目录，不对着 `_bin/logs` 测。
